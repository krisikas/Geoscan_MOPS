# Память о проекте Geoscan MOPS

Обновлено: 2026-11-05. Основание: чтение локального кода, конфигурации и README; без запуска сервисов, БД и оборудования. Это рабочие заметки, а не подтверждение работоспособности всего комплекса. Обновлять по мере изменений.

Актуальная задача пользователя: подготовка представления проекта без дрона, с планированием, фото, 3D и имеющимися записями полёта. Оценка препятствий и сценарий — в `DEMO_READINESS.md`. Приоритет ближайших работ — надёжность этой демонстрации. В `backend/data` обнаружены реальные локальные материалы (~2 GB), две GLB; старые AI-результаты преимущественно в папках без суффикса модели и текущим API не читаются. БД и визуальное отображение пока не проверены.

## Назначение и оценка состояния

МОПС — мониторинг и обследование поверхностей сооружений: оператор описывает задачу, AI строит маршрут, Pioneer Mini 2 собирает RGB/тепловые кадры, Metashape строит модель и ортомозаику, YOLO/CrackSAM выделяют дефекты. Интерфейс показывает план, фактическую траекторию, чат, изображения, маски и GLB.

По реализации это интеграционный прототип с существенным объёмом функциональности. Production-готовность не подтверждена: есть пробелы авторизации, ограничения управления полётом реализованы частично, инфраструктура и обработка ошибок требуют доработки. Заявленные в README метрики моделей и точный вариант YOLO локальным обзором не проверялись.

## Карта репозитория

| Каталог | Роль и точки входа |
| --- | --- |
| `frontend/` | React 19 + Vite, React Router, Three.js / React Three Fiber / drei; `src/App.jsx`, `src/context/AuthContext.jsx` |
| `backend/` | FastAPI, SQLAlchemy, PostgreSQL, JWT в HttpOnly cookie `mops_token`; `src/main.py`, `src/api/auth.py`, `src/api/projects.py` |
| `ai_service/` | FastAPI, запуск внешнего CLI `agy` подпроцессом; `main.py`, `prompts/planning_vla.md`, `prompts/flight_vla.md` |
| `pioneer_mcp/` | FastMCP → Pioneer SDK2; `src/__main__.py`, `src/server.py`, singleton `DroneRuntime` в `src/drone_runtime.py` |
| `telemetry_service/` | FastAPI, WebSocket телеметрии и кадров, передача кадров в backend, управление паузой съёмки и посадкой; `main.py` |
| `readme_photos/` | Иллюстрации документации |

`backend/src/cracksam/` содержит локальную реализацию SAM и адаптеров. `backend/src/services/fly.py` — старый отдельный TCP-путь; актуальный экран миссии запускает полёт через WebSocket. `grabber.py` практически пуст.

## Потоки данных и интерфейсы

1. Регистрация/вход через `/api/auth/*`. Основные CRUD-запросы `/api/projects/*` проверяют владельца проекта.
2. `MissionPage.jsx` → backend `POST /api/projects/{id}/plan` → AI `POST /plan` → `agy --print`. JSON разбирается регулярным выражением; маршрут и ответ сохраняются в PostgreSQL.
3. Реальный полёт: браузер → backend `/api/projects/{id}/stream_flight` → AI `/stream_flight` → `agy` с полётным промптом → MCP → SDK. Не считать вывод `tool` в чате самостоятельным исполнителем: backend лишь сохраняет и пересылает сообщения; инструменты вызывает внешняя агентная среда.
4. Браузер отдельно подключает `/ws/telemetry/{project_id}?ip=...` на порту 8002. Сервис опрашивает HTTP `/drone/position`, камеры `/main_camera` и `/thermal_absolute`, получает ориентацию через SDK. Cookie браузера пересылаются backend при загрузке кадров.
5. `ResultPage.jsx` управляет загрузкой/обработкой, получает статусы через SSE `/status/stream`; маски показываются поверх исходников. 3D — `AdvancedModelViewer.jsx`; визуализация маршрута — `RouteVisualizer.jsx`.

Модели БД: `User`, `Project`, `ChatMessage`. В `Project`: статусы AI/Metashape, список моделей, ошибка, `mission_status`, JSON `route_data`. `mission_status` не следует считать полноценным автоматом состояний: реализация потока полёта его не ведёт.

Данные на диске относительно cwd backend: `backend/data/projects/{id}/`. Папки `ai_input`, `ai_output_{yolo,cracksam}`, `metashape_input`, `metashape_project`, `metashape_ai_output_{yolo,cracksam}`, `thermal_input`. Результаты AI: прозрачный PNG и `_data.txt` с bounding boxes. Metashape: `project.psx`, `model.glb`, `orthomosaic.png`.

## Запуск и зависимости

- `start.sh` ожидает запуск из корня репозитория. Docker Compose поднимает только PostgreSQL :5432 и Vite :5173. MCP :9090, AI :8001, backend :8000 и telemetry :8002 работают нативно через `uv sync` / `uv run`.
- MCP по умолчанию слушает 127.0.0.1; фактический Streamable HTTP path задаётся в `server.py` как `/sse`. Поле `mcp_endpoint='/mcp'` в TransportConfig не применяется к серверу.
- Python-проекты требуют >=3.12. Настройки backend: `.env`, обязательный `SECRET_KEY`, `DATABASE_URL` или `POSTGRES_*`; фронтенд использует `VITE_API_BASE_URL`.
- `DRONE_IP` читается MCP при импорте. Подключение также принимает явный TCP-адрес, но HTTP-часть runtime продолжает использовать адрес из окружения.
- Внешняя зависимость `agy` и его доступ к модели/MCP не устанавливаются кодом сервиса. Точный провайдер/модель определяются внешней средой; упоминание Gemini в README не является настройкой в исходниках.
- YOLO: `YOLO_MODEL_PATH`, затем поиск в `weights/yolo/best.pt` и других локальных путях. `start.sh` задаёт `./best.pt`. При обзоре этот файл присутствовал (около 155 MB), папки `backend/weights/yolo` и `cracksam` были пустыми.
- CrackSAM требует `weights/cracksam/{sam_vit_h_4b8939.pth,CrackSAM_adapter_d32.pth}`; запускает отдельный Python-процесс на каждый снимок, выбирает CUDA или CPU (MPS здесь не используется).
- Backend требует Metashape Python API и рабочую лицензию. Локальный `pyproject.toml` ссылается на macOS wheel; присутствует и Linux wheel. Не менять эту пользовательскую настройку без задачи.
- README различает текущий локальный запуск и целевую production-схему. Не считать Dockerfile доказательством воспроизводимого production-развёртывания.

## Подтверждённые замечания по коду

### Высокий приоритет

1. **Авторизация управления полётом.** Backend `stream_flight` принимает WebSocket без проверки JWT/владельца, читает проект по одному ID и запускает AI. AI `/plan`, `/stream_flight` и telemetry endpoints также без аутентификации. AI и telemetry в `start.sh` слушают 0.0.0.0. Нужен единый контроль доступа и изоляция внутренних сервисов.
2. **Доступ к чужим кадрам.** Backend `upload_photo`, `upload_thermal`, `clear_photos` требуют вход, но не проверяют существование и владельца проекта: авторизованный пользователь может записывать/удалять кадры по чужому ID.
3. **Ограничения полёта неполны.** `DroneRuntime.__chk_bat()` использует `v = 8.0`, реальную батарею не проверяет. У ожидания `point_reached()` нет таймаута. Аргумент `speed` перемещения к точке не проверяется на предел/положительность. Нет общего блокирования конфликтующих миссий или единого владельца дрона.
4. **Проверки соединения могут сами падать.** В навигации проверки собраны в tuple: `__chk_sky()` вычисляется ещё до обработки результата `__chk()`. При отсутствии SDK-соединения возможно исключение вместо штатного JSON-ответа.
5. **Адрес дрона расходится.** `cmd_connect(tcp=...)` подключает SDK и камеру к переданному адресу, но позиция/сервопривод и часть телеметрии читают `__DEFAULT_TCP` из `DRONE_IP`. Выбор IP в UI может не примениться ко всем операциям.
6. **Ложный успех обработки.** Metashape подавляет ошибки экспорта GLB, построения/экспорта ортомозаики и возвращает путь, после чего backend выставляет `done`. `process_single_image_ai` также ловит ошибки моделей и возвращает `status: done`.

### Надёжность и качество

- Полёт управляется внешним агентом с `--dangerously-skip-permissions`; ограничения промпта не обеспечивают техническую изоляцию. Ответ планировщика не валидируется типизированной схемой маршрута с геометрическими пределами.
- Съёмка зависит от браузерного WebSocket. Подключение telemetry сначала удаляет предыдущие RGB/тепловые кадры; переподключение может уничтожить собранную серию. Pause-флаг и набор активных сокетов глобальны на процесс, не привязаны к миссии.
- UI emergency stop не проверяет `response.ok`, поэтому HTTP 500 может отобразиться как успешная остановка. Сервис вызывает `land()`, но не подтверждает фактическую посадку; разрыв агентного соединения не является подтверждением прекращения всех команд.
- AI/Metashape используют BackgroundTasks в API-процессе, `processing_locks` хранится только в RAM; нет устойчивой очереди, восстановления после рестарта и общей блокировки для нескольких workers. Общая YOLO-модель кешируется без явной сериализации конкурентного инференса.
- В YOLO пороги классов: 0 → 0.003, 1 → 1.03, 2 → 0.8, 3 → 0.00037. Порог 1.03 исключает класс при confidence <=1; очень низкие пороги требуют проверки на размеченной выборке. Не делать выводов о точности без данных.
- YOLO уменьшает исходник до максимальной стороны 5080 до тайлинга 640×640 (перекрытие 20%). CrackSAM уменьшает весь кадр до 448×448 и затем растягивает маску обратно: для тонких трещин на больших фасадах это потенциальная потеря деталей. Это два отдельных результата, объединение ансамбля в коде не подтверждено.
- Metashape строит модель и ортомозаику по ней; явная фасадная проекция и построение DEM, описанные в README, в этом pipeline не заданы. Пригодность результата для вертикальных фасадов требует проверки на реальной серии.
- Backend меняет схему БД при импорте (`ALTER TABLE`, `create_all`), ошибки ALTER подавляются. Есть несколько ручных скриптов миграции, Alembic отсутствует.
- `POST /{id}/start_flight` — `pass`; актуальный UI использует WebSocket, поэтому заглушка сама по себе не означает отсутствия запуска полёта.
- Хардкод `localhost` в межсервисных URL и telemetry URL браузера мешает контейнеризации и работе с другой машины.
- `backend/Dockerfile`: Python 3.10 против >=3.12 в проекте, Poetry вместо uv, вызов curl без явной установки curl, неоднозначный wildcard с двумя платформенными wheel. AI Dockerfile не устанавливает `agy`. Полная сборка контейнеров не проверялась.
- Cleanup `start.sh` завершает процессы по портам и `pkill`, хотя PID сохраняются: может затронуть сторонние процессы. Ошибки запуска не останавливают скрипт немедленно, проверка готовности БД отсутствует.
- Тестовая инфраструктура почти отсутствует: `backend/tests/` содержит только `__init__.py`; `test_history.py` читает реальную БД, аппаратные `test_*.py` не являются изолированной регрессией. В изученных файлах CI не обнаружен.

## Выполненные проверки 2026-11-05

- `frontend: npm run build` — успешно; основной JS chunk около 1.52 MB, gzip около 446 KB; Vite предупреждает о размере. Разделение 3D/страниц через lazy imports — возможная оптимизация.
- `frontend: npm run lint` — неуспешно: 49 errors, 10 warnings. Есть неиспользуемые переменные, пустые catch, замечания hooks/dependencies и setState в effects.
- AST-разбор 39 Python-файлов из `backend/src`, `ai_service`, `telemetry_service`, `pioneer_mcp/src` — без синтаксических ошибок. Это не проверка импортов, зависимостей и исполнения.
- Сервисы, Docker, фотограмметрия, инференс и полёты не запускались. Реальные метрики CV, аппаратные ограничения и поведение аварийной посадки не проверены.

## Рекомендуемый порядок дальнейшей работы

1. Закрыть авторизацию HTTP/WebSocket и проверку владельца; изолировать внутренние сервисы.
2. Ввести детерминированный исполнитель миссии с валидируемым маршрутом, реальными проверками батареи, таймаутами, отменой и единым арбитражем команд; LLM оставить планирование и интерпретацию сцены.
3. Исправить статусы/ошибки обработки и сохранить данные миссии независимо от браузера.
4. Добавить изолированные тесты доступа, отказов и отмены, затем очередь задач и миграции БД.
5. Проверить CV и фасадную фотограмметрию на эталонной серии; согласовать документацию с результатами. Затем привести развёртывание и frontend lint к воспроизводимому состоянию.
